# Colony Pod Action-menu join

`ui.colony_menu_join.v1` covers joining one owned first city through the
Colony Pod's actual Action-menu source slot 1. Two synthetic source profiles
change that row's wording while retaining its identity and shortcut data.
Starting with a ready Scout, each trace presses Tab twice, opens MENU and
Action, clicks the independently observed source-1 row, then presses Tab.

The declared city has one Doctor, zero workers/worked squares, zero stored
nutrients and nine stored minerals. Three healthy ready units share its tile.
Both applications guard that initial state. Every checkpoint records actual
selected role, city population/jobs/worked-square/store counters, surviving
unit roles/orders/movement and root/child menu visibility. City identity,
owner/count, paused year, unit identities/positions and companions remain
guarded. Pod consumption and citizen changes are observations, not fixture
callbacks or predicted results.

Reference recording executes the fingerprinted original after fresh setup or
verified original-created save loading, through ordinary Windows input and
independent pixel/native reads. Each complete case is repeated twice with
identical output and metadata using `compare.py record`. Only synthetic inputs
and observed structured outputs belong in the repository.

Native candidate replay uses mounted production controls and the existing
join controller/handler against real units, city and citizens. Initial setup,
scene nodes, frontend notifications and queued delivery are fixture boundaries;
no original assets or rendering are required. This is the owned-city join
context only: new-city founding, other population/terrain/faction contexts,
join limits, subsequent income, AI and full Action-menu parity are excluded.
